# Задачи пилота

## 0. Общий HTTP-контракт

- [x] 0.1 До реализации HTTP-задач создать `api/openapi.yml` с маршрутами и схемами из дизайна, правами, параметрами, сессиями, CSRF и примерами ошибок. Добавить проверку файла в CI и зафиксировать в инструкциях проекта его расположение и порядок обновления до кода. Проверить, что файл проходит валидацию и покрывает все маршруты дизайна.

## 1. Основание и учётные записи

- [x] 1.1 Перевести Java 25 с Maven на Gradle Wrapper, подключить Spring Boot, Spring JDBC, PostgreSQL и Liquibase. Проверить миграции на пустой БД и повторный запуск без сброса данных. Обновить команды сборки в README и инструкциях репозитория.
- [x] 1.2 Реализовать вход, выход, смену временного пароля и профиль. Проверить ограничение попыток, CSRF, закрытие сессии и отсутствие доступа к реестру до смены временного пароля.
- [x] 1.3 Реализовать создание первого администратора и управление участниками. Проверить независимость ролей, защиту последнего администратора, выдачу временного пароля и отзыв сессий после отключения, сброса и изменения ролей.
- [x] 1.4 Разделить бэкенд на пакеты `accounts` и `risks`. Архитектурным тестом проверить направление зависимости и доступ только к публичному интерфейсу соседнего модуля.

## 2. Серверная модель реестра

- [x] 2.1 Реализовать карточку, очередь и черновики по [схеме PostgreSQL](design.md#схема-postgresql), выдавая ID риска при создании. Проверить обязательные поля, оценки и категории, саморевью, видимость записей и сохранение ID при публикации и архивировании.
- [x] 2.2 Реализовать атомарное утверждение, указатель на неизменяемый снимок, события ревью и единственную правку в работе. Проверить, что БД отклоняет вторую незавершённую версию и ссылки публикации или события на версию другого риска. Проверить видимость прежней версии, отказ редактировать версию на ревью и `409` без частичной публикации при конкуренции отзыва и одобрения.
- [x] 2.3 Реализовать отзыв и закрытие первого предложения, отзыв и разблокировку правки. Проверить удаление из очереди, вывод причины в личной истории, повторную подачу с новым ID и приватность черновиков.
- [x] 2.4 Реализовать подтверждение оценки указанного опубликованного снимка, сроки пересмотра и архив. Проверить подтверждение при открытой правке, отклонение устаревшего снимка, конец месяца, сохранение даты при правке текста, требование причины завершения и сохранность истории.
- [x] 2.5 Проверять владельца при одобрении. Проверить отказ первой публикации или нового назначения при отключении между отправкой и одобрением, возврат для замены и успешное утверждение правки с сохранённым прежним владельцем.

## 3. Рабочий интерфейс

- [ ] 3.1 Связать Next.js с API входа, смены пароля и админки. Проверить в браузере создание участника, первый вход, выдачу роли и отключение.
- [ ] 3.2 Добавить таблицу, поиск, фильтры, карточку и историю, очередь и архив. Проверить в браузере полный путь автора и ревьюера, заметку о решении и состояние интерфейса после конфликта.
- [ ] 3.3 Сверить HTTP-ответы с `api/openapi.yml` контрактными тестами, включая `404` для приватной версии, ограниченные метаданные для разблокировки и `409` для устаревших действий. Запустить сборку и проверку типов Next.js, тесты Gradle и автономные сценарии и тесты HTML.

## 4. Эксплуатация и приёмка

- [ ] 4.1 Подготовить Compose и инструкцию оператора по внутреннему HTTPS, секретам, первому администратору, проверке готовности и откату. Проверить запуск из пустой БД и сохранность записей после перезапуска.
- [ ] 4.2 Настроить ежедневное резервное копирование вне сервера с хранением 14 дней. До встречи выполнить пробное восстановление и сверить версию и историю. До открытия доступа отозвать сессии, сверить аккаунты и роли и повторить сбросы после копии. Проверить, что старые сессии, отключённые аккаунты и пароли, заменённые после копии, не дают доступа.
- [ ] 4.3 Назначить одного ответственного за стенд и процесс. До запуска пилота зафиксировать самостоятельный прогон прототипа двумя коллегами: автора и ревьюера. Проверить, что они объясняют приоритет и различают предложение и утверждённую версию.
- [ ] 4.4 Провести одну рабочую встречу. Зафиксировать опубликованный реальный риск с действием, владельцем и датой возврата. При необходимости проверить пересмотр и завершение на отдельной тестовой записи. Записать замечания и подтвердить, что реестр остаётся доступен команде.
