# Назначение ответственного за контроль риска

## Контекст

Сейчас `risk_versions.owner_id` входит в поля предложения. При открытии правки владелец копируется из опубликованной версии. Поэтому хранение текущего назначения в версии связывало бы его с утверждением правки и могло бы восстановить прежнего ответственного. Публикация и архивирование уже используют транзакцию с блокировкой строки `risks`, а журнал `risk_events` задаёт общий порядок событий.

Мотивация описана в [предложении](proposal.md), наблюдаемое поведение — в [дельте требований](specs/risk-register/spec.md).

## Данные и история

- Текущее назначение хранится в `risks.assignee_id` с внешним ключом на участника. Поле допускает `NULL`. Отдельный счётчик `assignment_revision` начинается с `1` и увеличивается только при изменении назначения. Хранение назначения в строке риска позволяет использовать существующую блокировку. Вариант с отдельной таблицей потребовал бы дополнительной записи и координации двух строк при архивировании.
- Создание черновика и первая публикация оставляют назначение пустым. Утверждение правки, подтверждение оценки и архивирование сохраняют текущее назначение и его ревизию. Изменение назначения сохраняет указатель на опубликованную версию и дату оценки, от которой считается срок пересмотра.
- Владелец исключается из полей создания, изменения и валидации предложений. Старый `risk_versions.owner_id` хранится для чтения исторических снимков. Новые версии создаются с пустым значением, в том числе при открытии правки исторической версии. При сохранении старого черновика историческое поле не участвует в записи. Для строки «Предложил» используется автор версии, связанной с первым по порядку событием `APPROVE`.
- Журнал `risk_events` получает два действия: `ASSIGNMENT_CHANGED` для пользовательского изменения и `ASSIGNMENT_MIGRATED` для переноса. Событие содержит время, идентификаторы прежнего и нового ответственного и ссылку на версию, опубликованную в момент записи. Инициатором пользовательского изменения остаётся участник. `actor_id` допускает `NULL` только для события переноса, у которого источник системный. Единый журнал сохраняет порядок событий без дополнительного объединения истории.
- События назначения видны всем участникам с доступом к опубликованной карточке. При формировании исторических снимков по-прежнему используются события `APPROVE`. Приватность предложений и их событий проверяется по действующим правилам.

## Запись назначения

1. `RiskService` внутри одной транзакции блокирует строку риска через существующий путь `FOR UPDATE`. Отсутствующий и неопубликованный риск дают `404`. Для опубликованного риска проверяются роль ревьюера или администратора, активное состояние и ревизия назначения. В контекст участника из `AccountDirectory` добавляется признак администратора.
2. Недостаточная роль даёт `403`. Для архивного риска и устаревшей ревизии возвращается `409 RISK_CONFLICT`. Проверка ревизии выполняется до проверки совпадения значений, поэтому устаревший запрос отклоняется и при совпадении с текущим назначением.
3. Для непустого назначения через `AccountDirectory` блокируется строка кандидата и проверяется активность аккаунта. Недоступный или отключённый кандидат даёт `409 ASSIGNEE_INACTIVE`. Старая отметка о назначении доступна в карточке, пока ответственного явно не заменят или не снимут.
4. При актуальной ревизии и совпадающем значении операция возвращает карточку без изменения ревизии и истории. При изменении запись назначения, увеличение ревизии и добавление события фиксируются одной транзакцией. Согласие ответственного и уведомления в операции отсутствуют.

## HTTP и интерфейс

- Первым меняется HTTP-контракт. `PATCH /api/risks/{id}/assignment` принимает два обязательных поля: `assigneeId` (UUID или `null` для снятия) и `expectedAssignmentRevision` (целое число от `1`). Существующие проверки сессии и CSRF применяются к новому маршруту. Ответ `200` содержит обновлённую опубликованную карточку.
- Карточка возвращает автора первого предложения, текущего ответственного и ревизию назначения. Список возвращает текущего ответственного. Для ответственного передаются идентификатор, отображаемое имя и признак активности либо `null`, если назначения нет. Поле прежнего владельца доступно в историческом снимке и допускает `null` для новых версий. События назначения передают прежнего и нового ответственного либо `null` на соответствующей стороне перехода. Системный источник определяется по действию переноса.
- Параметр списка `assignee` заменяет `ownerId`. UUID фильтрует активный список или архив по текущему назначению. Значение `needs-assignment` доступно в активном списке и включает риски без назначения и с отключённым ответственным. Активность определяется по текущим данным аккаунта.
- Next.js загружает начальные данные прежним серверным путём. После первого утверждения открывается опубликованная карточка. В активной карточке ревьюер или администратор видит действие назначения, а список кандидатов берётся из существующего `GET /api/participants`. Карточка и таблица показывают имя, «Не назначен» или имя с отметкой «Требуется замена». Общая история показывает переход между назначениями и подпись «Перенесено из прежнего реестра» для системной записи.
- После сохранения обновляются карточка, история и список с текущими фильтрами. При `RISK_CONFLICT` интерфейс предлагает обновить карточку. При `ASSIGNEE_INACTIVE` показывает пояснение и обновляет участников для повторного выбора.

## Миграция и выпуск

1. Добавить отдельный changeset Liquibase. В рамках его транзакции перенести непустой `owner_id` из версии, на которую указывает `risks.published_version_id`, и записать по одному событию переноса. В выборку входят архивные риски и отключённые владельцы. Неопубликованные предложения и открытые правки не участвуют в переносе. Ревизия перенесённого назначения начинается с `1`.
2. На копии базы предыдущего релиза сверить количество и значения переносов, исторические снимки и события. Повторно запустить приложение и проверить отсутствие дублей. Проверить также миграции при запуске с пустой базой.
3. В согласованное окно обслуживания закрыть доступ на запись, сохранить резервную копию PostgreSQL и версии образов. Обновить API и фронтенд вместе, поскольку контракт меняется несовместимо. До открытия доступа сверить переносы и их события, проверить вход и карточки активного и архивного риска.
4. При сбое до открытия доступа остановить API и фронтенд, восстановить копию в пустую базу и запустить прежние образы с этой базой. Сверить данные, проверить вход и открытие карточек до возобновления записи. Восстановление в пустую базу исключает конфликт с внешними ключами, добавленными новой миграцией.
