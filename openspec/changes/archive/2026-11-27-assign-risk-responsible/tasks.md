Сценарии приёмки описаны в [дельте требований](specs/risk-register/spec.md), технические решения — в [дизайне](design.md).

## 1. HTTP-контракт

- [x] 1.1 Обновить `api/openapi.yml` до изменений сервера и клиента. Описать запрос и ответ назначения, права и ошибки, фильтр `assignee`, автора и назначение в карточке, события назначения и прежнего владельца в историческом снимке. Убрать владельца из полей предложений. Проверить контракт через `python -m openapi_spec_validator api/openapi.yml`, обновить типы командой `npm run api:generate` и проверить их через `npm run api:check`.

## 2. Данные и сервер

- [x] 2.1 Добавить changeset Liquibase для текущего назначения и событий журнала. Перенести владельца опубликованной версии и создать по одному системному событию на назначение. Проверить на копии базы предыдущего релиза активный и архивный риски, владельца-автора, отключённого владельца, открытое и неопубликованное предложения. Сверить исторические снимки, проверить отсутствие дублей после перезапуска и успешный запуск с пустой базой.
- [x] 2.2 Убрать владельца из создания, сохранения, отправки и утверждения предложений. Получать автора первого предложения из первого утверждения, отдавать текущее назначение в карточке и списке, сохранить прежнего владельца в исторических снимках. В E2E на реальном API проверить публикацию без ответственного, прежний идентификатор риска и отображение первого автора после утверждения правки другого участника.
- [x] 2.3 Реализовать изменение назначения с проверкой роли, публикации, активного состояния, ревизии и активности кандидата. Записывать назначение и событие одной транзакцией. В E2E проверить роли обычного участника, ревьюера и администратора без роли ревьюера, CSRF, запрет для неопубликованного и архивного риска, два запроса с одной ревизией, устаревший запрос с совпадающим значением и повторное сохранение с актуальной ревизией. Сверить HTTP-ответы и убедиться, что отклонённые и повторные запросы не добавляют событий.
- [x] 2.4 Добавить события назначения в чтение общей истории и фильтрацию списка по текущему назначению. В E2E проверить назначение, замену и снятие, данные об инициаторе и участниках перехода, видимость опубликованной истории и приватность открытого предложения. Проверить фильтр «Требует назначения» для пустого назначения и отключённого ответственного, а также отклонение выбора кандидата, отключённого после загрузки карточки.
- [x] 2.5 В E2E проверить взаимодействие с жизненным циклом. Сменить ответственного при открытой правке и затем утвердить её. Сверить, что смена не изменила опубликованную версию, дату оценки или срок пересмотра, а утверждение сохранило назначение. Проверить сохранность последнего назначения в архиве и последовательность результата при конкуренции назначения с архивированием.

## 4. Интеграция и выпуск

- [x] 4.1 Запустить `npm run build`, `npm run lint`, `npm run typecheck`, `npm run test:components` и `npm run test:e2e` из `frontend/` на Node.js 24. Для E2E использовать отдельный стенд Spring Boot и PostgreSQL. Собрать бэкенд через Gradle Wrapper на JDK 25. Зафиксировать результаты и оставить задачи с непрошедшими обязательными проверками открытыми.
- [x] 4.2 Отрепетировать согласованное окно обновления на отдельном стенде с копией данных предыдущего релиза. Проверить совместный запуск API и фронтенда, сверку переноса, вход и просмотр активного и архивного риска. Проверить восстановление копии и прежних образов до возобновления записи.

Проверки 4.1 прошли на Node.js 24.20.0 и JDK 25. Компонентный набор использовал заглушку OpenAPI и Chrome. Оба сквозных сценария прошли на отдельном стенде с Next.js, Spring Boot и PostgreSQL 17.

Репетиция 4.2 прошла в отдельном проекте Docker Compose `risk-release-rehearsal` на копии локальной базы предыдущего релиза с PostgreSQL 17. В копию добавили тестовый аккаунт и один архивный риск. После совместного обновления API и фронтенда сверили четыре переноса и четыре системных события без расхождений. Десять неопубликованных рисков остались без назначения, исторические версии и прежние события совпали с исходными.

Вход и просмотр активной и архивной карточек через Chrome и API прошли до обновления, после обновления и после отката. Восстановление поверх обновлённой базы с `pg_restore --clean` остановилось на внешних ключах миграции. Копию успешно восстановили в пустую базу и запустили прежние образы API (`edf087b6b9b2`) и фронтенда (`ccc50485646c`). Сверили риски, версии, события, аккаунты, сессии и журнал миграций до возобновления записи.
